# Privacy design

PrivacySpec must not create a new sensitive-data artifact while observing application behavior.
Data minimisation is an architectural boundary, not an output formatting preference.

## Data lifecycle

High-confidence browser input values are captured into bounded, test-scoped registries. DOM
classification uses explicit autocomplete intent or corroborated bounded control metadata for the
supported email, telephone, password, name, postal-address, full birth-date, explicit
account-identifier, payment-card, gender-identity, and job-title categories. Gender identity and
job title use exact autocomplete intent only. The worker recomputes the classification before
admission. Configured custom classifiers are normalized into bounded exact declarative tables;
only those tables enter the init script, and the worker recomputes custom matches from bounded
control metadata. A caller-supplied bounded configuration ID identifies the table's semantics;
matcher tables and matcher-derived digests never enter artifacts. When the experimental option is
enabled, recognized email/phone values from bounded
first-party JSON responses enter the same registry after response parsing completes. Network,
response, console, storage, and composed-request-fixture argument material is retained only in
bounded browser/test-worker memory. API response bodies are never read and API arguments/responses
never become sensitive sources.
Correlation derives semantic flows, runtime hygiene classifies supported browser-input emails, and
then fixture teardown clears the transient registries. Separately, the opt-in storage-state scanner
reads only explicit bounded JSON files and releases its parsed state after structural classification.

```text
browser/test-worker memory -> deterministic correlation -> sanitized semantics -> disposal
```

The implementation does not use a stable raw-value hash for baseline identity. Exact, encoded,
Base64, and SHA-256 representations are generated transiently only to find a match.

## Persisted data

PrivacySpec attachments, run-part artifacts, latest-run handoffs, baselines, baseline proposals,
terminal/Markdown summaries, JSON reports, inventory exports, test-data hygiene exports, and
evidence exports may contain:

- data category and source confidence;
- bounded sanitized control metadata and semantic classification evidence;
- response source kind plus normalized first-party origin, endpoint, and JSON location;
- sink kind and structured field location;
- request surface (`browser` or `api-request`);
- classifier compatibility as `{ mode: "builtin-only" }` or `{ mode: "custom", id }` in privacy
  attachments, privacy baselines/latest runs, and run parts only;
- recipient origin/host and first-party classification;
- normalized endpoint and deterministic transform class;
- Playwright test file, title, and project in occurrence evidence;
- rule ID, technical-control references, and regulatory relevance;
- aggregate counts, diagnostics, and timing;
- count-only browser/context/page/navigation/network/console observation coverage and sanitized
  coverage-status diagnostics;
- sanitized response coverage and skip-reason counts;
- count-only browser-engine capability and API-request coverage/skip facts;
- hygiene verdict, reason signal, category, source kind, and sanitized test/control attribution;
- explicitly supplied commit/build identifiers and source-report/evidence timestamps;
- storage-state input indexes, local Git status, finding status, and bounded structural,
  credential-semantic, and direct personal-data-shape counts.

They must not contain raw input values, request bodies, console arguments, storage values,
passwords, tokens, observed email domains, or screenshots/traces generated by PrivacySpec.
Baselines additionally exclude test identity and contain only stable semantic review identities.
Baseline proposals contain only one module, canonical add/change/remove actions, stable semantic
identities, deterministic proposal IDs, fixed counts, timestamps, and SHA-256 digests of sanitized
artifacts/proposal content. They do not contain source paths, test attribution, occurrence
evidence, fingerprint display values, or parser diagnostics.

Runtime JSON artifacts, run parts, baselines, baseline proposals, summary files, inventory exports,
test-data exports, and evidence exports are written atomically with mode `0600`. Run parts are
create-only, reject symlinks, use path-safe bounded run/configuration identifiers, and contain
sanitized semantic payloads only. Proposal and selective-acceptance paths reject symbolic-link
components and source/output collisions; their strict readers additionally verify canonical order,
bounded sizes, deterministic identities/digests, and reject common raw email, international-phone,
credential-assignment, query-string, encoded, and control-character payload shapes. Other strict
readers reject unsupported schemas, unknown fields/unions, unbounded depth/items, unsafe control
characters, symlinks/non-regular files, inconsistent summaries, and unsanitized absolute/traversal
test paths before rendering. Attachment v1–v5, inventory v1/v2, and evidence v1/v2 use exact
version-specific readers. Evidence reconstructs mapping records
through a field allowlist and accepts only bounded, safe explicit build identifiers; it does not
infer metadata from Git or the environment. Inventory
CSV cells that could be interpreted as spreadsheet formulas are prefixed defensively; test-data and
evidence output do not offer CSV. Default runtime paths are ignored by Git. Users remain responsible
for protecting CI artifacts and for avoiding other Playwright reporters, traces, screenshots, or
application logs that may independently retain test state.

The GitHub Step Summary and the uploaded schema-v5 JSON report are additional sanitized CI
persistence surfaces. The composite Action renders only a strict report, never copies parser
errors into Markdown, and stages the exact validated JSON with mode `0600` before upload. GitHub
repository owners remain responsible for workflow permissions, artifact visibility, access
control, retention settings, and deletion; private local file mode does not control GitHub-hosted
artifact access.

Shard/process callers retain only distinct sanitized parts and aggregate locally before invoking
the Action. Per-part artifacts never contain baseline conclusions or latest-run eligibility. The
Action remains post-processing-only and does not discover, download, or coordinate shards.

## Runtime test-data hygiene

Runtime hygiene reuses raw email values that the browser-control observer already holds
transiently. It does not collect another source class. Domain parsing, Unicode/IDNA normalization, IANA-reserved
matching, and suite-configured matching happen before the source registry is cleared. The
classifier performs no DNS or other network lookup and never stores either the email or its domain
in an attachment, report, rendered review, diagnostic, or configuration echo.

`SYNTHETIC` means only that a reserved or explicitly configured domain rule matched.
`REVIEW_REQUIRED` means only that no such rule matched; it does not mean the value identifies a
person or the domain is routable. `UNASSESSED` means the supported conservative email shape did not
apply. The wording follows the [BfDI June 2025 test-data guidance](https://www.bfdi.bund.de/DE/Fachthemen/Inhalte/Technik/Kurzposition_Testdaten.html),
which prioritizes non-personal/anonymous or fully synthetic data before pseudonymous and unchanged
personal data. Reserved matching follows [IANA's example-domain guidance](https://www.iana.org/help/example-domains)
and special-use semantics. These references inform a technical review prompt, not a legal
compliance conclusion.

## Explicit storage-state hygiene

The separate `storageStateScanSchemaVersion: 1` command scans only explicitly supplied regular
Playwright storage-state/auth JSON files, rejects any symlink in an input path, and never
crawls a directory or repository. Each file is limited to 1 MiB; parsed input is limited to depth
12 and 50,000 JSON nodes. The raw buffer is overwritten after classification and parsed/string
references are released. JavaScript garbage collection cannot provide a general zeroization
guarantee, so the scanner promises minimization and non-persistence rather than memory forensics
resistance.

Output replaces every source path with a one-based input index and retains only cookie/origin/
localStorage counts, common credential-name/HttpOnly counts, direct email/phone-shaped value counts,
and local `TRACKED`, `IGNORED`, `UNTRACKED`, or `GIT_UNAVAILABLE` status. Raw JSON, cookie and
localStorage names/values, domains, origins, and input paths are never returned or rendered.

Credential-bearing state is `REVIEW_REQUIRED` when Git reports the file tracked or untracked, or
when Git status is unavailable and ignore protection cannot be established. An ignored local file
is `INFORMATIONAL`. Both results remain technical hygiene signals: ignored does not prove a file was
never exposed, and review-required does not prove publication, exposure, compromise, or a legal
outcome. This is grounded in [Playwright's authentication-state warning](https://playwright.dev/docs/auth).
Headers, sessionStorage, IndexedDB, application-specific credentials, nested values, HAR, trace ZIP,
HTML reports, and static test source remain outside the pilot.

## Processing boundary

All processing is local. PrivacySpec has no telemetry, hosted backend, user account, network
lookup, or AI dependency. Static regulatory/control mappings are shipped with the package.

## Safety bounds

Source counts and value sizes, sink entries and retained bytes, request body size, console
serialization, URL/path length, correlation comparisons/bytes, and output flow counts are bounded.
Reaching one of these collection or correlation bounds produces a sanitized informational
diagnostic and makes the run ineligible for a baseline update rather than silently presenting
incomplete evidence as complete.

The DOM classifier retains the existing six-character source minimum because the correlator uses
exact substring matching. This deliberately excludes short DOB/card components, short country or
postal values, and other low-uniqueness strings that could otherwise over-match sinks or over-redact
sanitized metadata. Card numbers require a non-repeated 12–19 digit Luhn-valid shape; full card
expiry and birth-date values receive bounded date validation. These are technical hygiene checks,
not proof of a real person, active account/card, PCI scope, or legal status.

Custom classifier configuration is limited to 64 classifiers, 32 alternatives per classifier,
512 alternatives total, 200-character matcher literals, and per-classifier 6–4,096-character value
bounds. Only exact normalized machine/accessibility metadata is supported. Configuration errors
use fixed wording and never echo matcher literals. Ambiguity produces only sanitized aggregate
diagnostic evidence, admits no category, and prevents a complete baseline-eligible run.

Non-empty custom classifier tables require `sources.customClassifierConfigurationId`; built-in-only
configuration forbids it. IDs are 1–128 safe ASCII characters and are persisted only as compatibility
provenance, outside per-flow semantic identity. Reordering an unchanged table keeps the ID; any
semantic matcher/category/confidence/bound change requires a new ID. Missing, unavailable, or
mismatched state suppresses privacy known/new/resolved conclusions and selective proposals without
changing dependency, security, or runtime baseline completeness. A complete current latest run may
still carry the new configuration so an explicitly confirmed whole-baseline update can reaccept it.
Legacy v1 privacy artifacts containing custom categories remain configuration-unavailable and are
never automatically bound to an ID.

The composed API-request observer reuses the 1 MiB body, 1,000 network-sink, and 16 MiB retained
material bounds. Each call also has one depth-8, 4,096-node, 1,000-entry budget and a 1,024-character
property/location limit. It inspects only named option descriptors and bounded enumerable own data
properties without invoking accessors or enumerating prototype descriptor tables. Sparse/deep/cyclic
objects, strings, buffers, URL parameters, forms, headers, cloning, and serialization are bounded
before retention. Work/material exhaustion records `materialLimit` once, discards partial body
material, and marks the body truncated. Sink or aggregate retention exhaustion disables later body
inspection while preserving exact delegation and sanitized final URL/status/header/cookie facts.
Streams, files, proxies, and unsupported objects retain count-only skip reasons; response bodies are
never read. Every observed API call remains partial because stable Playwright APIs do not expose
guaranteed injected headers, cookies/auth, or every redirect hop. Disabled detection does not
inspect call arguments.

Experimental response discovery additionally enforces 256 KiB per response, 2 MiB cumulative
retained response material per test, a four-operation concurrency limit, bounded queued work, and
JSON depth/node/value/source limits. Unknown-length and oversized bodies are not read. Skips are
reported as aggregate coverage statistics, mark observation coverage `PARTIAL`, and make secondary
analysis inconclusive without changing the functional Playwright result. Read buffers are
overwritten after parsing; raw JavaScript strings are dereferenced for garbage collection before
fixture teardown.

The coverage tracker retains object identity only in test-scoped `Set`/`Map` instances and
persists only non-negative aggregate counts. It does not retain URLs, console messages, request
metadata, context options, or page content. Coverage diagnostics are fixed sanitized messages and
never interpolate application data. Listener maps and object references are cleared at teardown.

### Unknown-length JSON decision

Response discovery deliberately skips JSON responses without a valid `Content-Length` header.
Playwright's stable [`response.body()` API](https://playwright.dev/docs/api/class-response#response-body)
returns the complete body as a `Buffer`; it does not expose a maximum-size or streaming read. Reading
an unknown-length body and truncating it afterward would therefore increase coverage by abandoning
the 256 KiB admission bound.

The Chromium DevTools alternatives do not currently provide an acceptable passive replacement:

- [`Fetch.takeResponseBodyAsStream`](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/#method-takeResponseBodyAsStream)
  requires the response to be paused and says the request cannot then be continued as-is. Cancelling
  or replaying the response would change application behavior.
- [`Network.streamResourceContent`](https://chromedevtools.github.io/devtools-protocol/tot/Network/#method-streamResourceContent)
  is experimental and returns data buffered before streaming was enabled. Enabling it only after
  classifying response headers cannot prove that no more than 256 KiB has already crossed the
  observer boundary.

For a declared length at or below 256 KiB, the header is the pre-read admission gate. PrivacySpec
also checks the returned buffer's actual size and rejects and overwrites it if the declaration was
wrong. This guarantees that PrivacySpec never parses or retains a response over the limit, but the
stable Playwright API cannot prevent Playwright or the browser from having already buffered that
response. Documentation and pilot conclusions must preserve that distinction.

Unknown-length support remains a future experiment, not an implementation commitment. Any proposal
must first prove a hard 256 KiB maximum—including lookahead, already-buffered data, and decoded
bodies—across frames, workers, service workers, caches, teardown races, and both supported
Playwright versions, without interception or changed application timing. Until then, aggregate
`unknownLength` coverage is the safe result.

## Known limits

PrivacySpec cannot observe backend-to-backend transfers after a browser request completes. Its
experimental response mode inspects only known-length, first-party JSON for email and phone key/
shape pairs; it does not inspect third-party or non-JSON responses, classify other response fields,
or infer that a response value caused later application behavior. It does not inspect arbitrary
JavaScript transformations, WebSocket payloads, deep service-worker behavior, or IndexedDB.
Unclassified data should not be interpreted as absent.

Firefox/WebKit instrumentation is opt-in and experimental. Ungated attempts retain functional
execution but do not run PrivacySpec observers and fail closed as unsupported. The request-fixture
experiment cannot detect calls through `page.request`, `context.request`, or manually created
`playwright.request.newContext()` objects.

Application code and unrelated Playwright tooling can still persist test data. Independent pilot
validation showed that Playwright's own error-context artifact can retain entered form state, so
privacy-safe evaluation should disable unnecessary traces/screenshots/error-context copying and use
generated, non-production data.
